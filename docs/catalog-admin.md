# Persistent catalog administration

Implemented locally after the source-grounded public catalog. This is a real database-backed
vertical slice, not the browser-only `/workspace` demo. The static public preview does **not**
include login or administration and cannot save catalog changes.

## What is implemented

- `/admin/catalog`: server-authorized product list, search, status filter and pagination;
  create/edit name, description, category, designation, price, currency, visibility,
  structured specifications and references to approved shipped public assets
- Fixed prices travel as decimal strings and are stored as `NUMERIC(18,2)`; on-request
  prices are null. No KZT assumption or invented product prices. ISO currency is explicit;
  `APP_CATALOG_ALLOWED_CURRENCIES` optionally limits the accepted codes
- Draft/published/hidden states; hide is recoverable and restore returns to draft,
  requiring deliberate republishing
- Optimistic `version` checks: a stale save returns HTTP 409 without overwriting newer work;
  the editor keeps the unsaved draft and offers explicit reload. Save is disabled in conflict
- Dirty Cancel/Close and internal-link navigation confirmations; browser refresh/close warning
- Stable `public_key` for the original 238 IDs, separate internal UUID, category keys and
  source ordering, full structured source/spec/media/family/variant evidence
- Transactional before/after audit for edits, create, hide and restore
- API-backed public listing, detail, comparison and local selection. New items are reachable
  without rebuilding. Hidden/unpublished items disappear from public API and saved selections
  label them unavailable rather than looking up a stale bundled record

## Database and API

Migration `e90a41c37b28` follows `d6b2e8f09a12`. Existing product slugs become their stable public
keys; existing rows default to on-request pricing. JSON specifications/provenance/media and
immutable original `source_data` are added. Raw source_data is retained for administrator
review/import provenance, omitted from public responses.

Admin routes require an active user and active organization membership whose role is global
(`role.organization_id IS NULL`) and grants `catalog.manage`:

- GET `/api/v1/admin/catalog/categories`
- GET/POST `/api/v1/admin/catalog/products`
- GET/PATCH `/api/v1/admin/catalog/products/{uuid}`
- POST `/api/v1/admin/catalog/products/{uuid}/hide`
- POST `/api/v1/admin/catalog/products/{uuid}/restore`

PATCH, hide and restore require the current integer version. Uniqueness conflicts and
optimistic conflicts are distinct 409 error codes. Product/category/price/spec/media validation
is server-side. No file upload or remote asset URL is accepted. The approved public asset
manifest is generated by `python scripts/update_catalog_assets.py` and checked with `--check`.

The migration creates a platform catalog-manager role but assigns **no** memberships. Normal
organization administrators cannot grant that global role or otherwise escalate platform
permissions via role changes or invitations. The DEV seed creates a distinct
`catalog@demo.example` account with the existing DEV-only password documented in README;
`admin@demo.example` remains a tenant administrator and receives 403 from the catalog admin API.
Do not seed DEV accounts in production.

## Import the reviewed 238 records

The PDF chunks contain 224 records. Nineteen reviewed web records include five overlaps.
The small generated `database-overlay.json` combines these exactly as the public frontend
already does: 238 distinct records, with every original ID, family relationship and source page.
Regenerate only after a reviewed source-data change:

```sh
node scripts/export-catalog-overlay.mjs
```

With dependencies installed and a migrated database, run from the repository root:

```sh
(cd backend && alembic upgrade head)
PYTHONPATH=backend python backend/scripts/import_catalog.py --dry-run
PYTHONPATH=backend python backend/scripts/import_catalog.py
```

For Compose, mount only the reviewed catalog input directory read-only:

```sh
docker compose run --rm -v "$PWD/docs/catalog-import:/catalog:ro" backend \
  python -m scripts.import_catalog --catalog-dir /catalog --dry-run
docker compose run --rm -v "$PWD/docs/catalog-import:/catalog:ro" backend \
  python -m scripts.import_catalog --catalog-dir /catalog
```

The importer validates chunk hashes/counts and the merged index, then inserts missing records
in one transaction. Reruns skip existing public keys, including edited or hidden records:
prices, descriptions, status, media and optimistic versions are never reset. Any invalid input
or identity/SKU collision rolls back the whole import. It creates no accounts, grants or prices.
Existing synthetic DEV products remain separate; a seeded development database can therefore
contain the 238 reviewed records **plus** the synthetic fixture. Do not use DEV seed for a real
catalog deployment.

## Choose the data source explicitly

- `/catalog?source=api`: current published database records, including live details,
  comparison and `/selection?source=api`
- `NEXT_PUBLIC_CATALOG_SOURCE=api`: make the database authoritative at frontend build time;
  query parameters cannot reopen stale bundled products
- `NEXT_PUBLIC_CATALOG_SOURCE=static` or `/catalog?source=static`: bundled reference snapshot
- `?source=demo`: existing synthetic UI fixtures

Changing a NEXT_PUBLIC value requires rebuilding the frontend. Compose passes the selected
mode as a build argument. The development default remains static for compatibility with
existing preview workflows. API failures never silently switch to static data. A separately labelled reference-snapshot
link exists only in the development/static build. An explicitly live build cannot expose hidden
items by changing the source query parameter; retain static preview as a separate deployment. Live and static local selections use different
storage keys so a public-key match cannot accidentally reuse an old snapshot's price or status.
CSV export excludes unavailable live items and treats formula-looking text as literal text.

`npm run build:preview` always forces static mode and removes `/admin`, `/login`, `/b2b`,
`/ai` and the mounted authentication provider. It cannot serve as the admin deployment.
The standalone frontend Docker image now explicitly copies `public/` so source illustrations
and original catalog-page assets are available in the runtime image.

## Verification

Run the normal checks and the dedicated browser suite:

```sh
(cd backend && ruff check . && pytest)
python scripts/check_frontend_env.py
python scripts/update_catalog_assets.py --check
(cd frontend && npm run lint && npm run test:unit && npm run build && npm run build:preview)
# Against running API/frontend after DEV seed and reviewed-catalog import:
(cd frontend && npm run test:e2e:admin)
```

The browser suite covers anonymous/tenant denial, create/reload/price persistence, public detail,
comparison/selection, hidden visibility, draft restore, dirty cancel and stale-save conflicts.
CI imports the reviewed records into its disposable Compose database before running E2E.

Local verification status for this slice is recorded in `catalog-admin-validation.md`.

## Production remains blocked pending infrastructure work

This slice intentionally does not weaken the existing startup security gates. A production
release still requires:

1. Approved same-site HttpOnly cookie/BFF session transport and CSRF policy; current DEV
   sessionStorage bearer transport is explicitly rejected by production configuration
2. Implemented distributed rate limiter; the in-process memory limiter is rejected
3. A real file scanner and a working approved object-storage provider; scanner noop is rejected,
   S3 is still a stub. This slice avoids uploads by accepting approved shipped asset references
4. A provisioned PostgreSQL database, reviewed migration/backup/rollback process, production
   application configuration and secure secrets
5. Explicit authorized provisioning of real platform catalog-manager membership; migration
   creates no access grants and the frontend cannot promote a tenant administrator
6. PostgreSQL migration upgrade/downgrade/schema-check and real browser E2E on the exact
   published commit, then an authorized deployment. Nothing here merges or deploys by itself

The production dependency audit was unblocked by moving PyJWT from vulnerable 2.13.0 to 2.15.1;
no audit exceptions or security checks were removed. Known DEV-only dependency advisories found
by an optional all-environment audit are documented in the validation report separately.
