## Что означает оставшаяся группа из 73

Это проверки цепочки historical catalog approvals и её отрицательных/положительных сценариев: backend-security, frontend-security, KTPB, PTMM, browser, visual, source assets, execution choices, measurement columns и joint-site. Они не просто проверяют названия удалённых страниц. Они связывают согласование с точными SHA256 версий кода, тестов, CI, пакетов, lock-файлов и исходных материалов.

Конкретные первые причины: изменённые `.github/workflows/ci.yml`, `frontend/package.json`, `backend-node/src/domain/catalog.js`, `frontend/components/catalog/CatalogSourceEvidence.js`, `frontend/e2e/catalog.spec.js`. Часть тестов падает раньше ожидаемой намеренной мутации, потому что уже начальное состояние fixture не соответствует зафиксированному эталону. Поэтому одна исходная несовместимость даёт несколько разных падений.

В актуальном дереве 106 входов `joint-site-integration/clearance.json` отличаются от записанных хешей. Полный список с ожидаемыми и текущими SHA256 — `stale-review-inputs.json`. Это количество несовпадающих входов одного согласования, **не число обнаруженных функциональных дефектов**.

Согласование имеет статус `approved-bounded-joint-site`, но относится к старым candidateCommit/candidateTree. Наличие строки `approved` само по себе не даёт права применять его к изменённым файлам. Текущий fail-closed отказ сохраняется.

## Почему не подменены ожидаемые хеши

Проверены существующие архивные JSON, доступная история Git и локальные Git-объекты. Исторические helpers содержат лишь дельты: для части файлов они обращаются к текущему дереву, а для части сохраняют только SHA256 без самих байтов. Импортный коммит `53f4ec6` уже отличается от более ранних согласованных эталонов.

Например, точные байты с SHA256 `66df3a538df94b840a91a34da5e9476b1f405cd00fcbf3fe009327599e5a869d` для старого CatalogSourceEvidence и `59a72501f5c3562a8f7985f722471ee20f85b06522f4885ef635df4e871b29ca` для Design/index.html в доступных объектах не найдены. Из одного SHA256 нельзя восстановить файл. Попытка собрать неполный test-only snapshot выявила следующие отсутствующие входы; она отменена и в изменения не включена.

Для корректного устранения этой группы нужен один из двух путей:

1. Получить полный оригинальный эталон согласованной версии и сделать исторические unit-fixtures полностью автономными. Реальные проверки текущего дерева при этом должны продолжать отклонять старое согласование.
2. Провести новую независимую проверку изменённых входов и оформить новое ограниченное согласование для текущей версии, сохранив исторические согласования и отрицательные проверки. Изменения касаются также авторизации, backend и зависимостей, поэтому это не только обновление тестов страниц.

Ни один путь не заменён фиктивным `approved`, автоматическим пересчётом всех ожидаемых хешей, ослаблением assert, пропуском или исключением тестов. Это оставшееся ограничение, а не завершённое исправление 73 проверок.
